# Physics-Verified 3D CAD DSL — Design and Development Specification

> Status: authoritative design direction for extending the current LLM-CAD-Editor project.
>
> This document combines the original physics-CAD concept, the repository design review, and an
> implementation roadmap. It does not claim that the planned physics features already exist. Current
> implementation status remains documented in [`compiler_status.md`](compiler_status.md).

---

## 1. Executive Summary

The target system is a CAD language in which an engineer describes geometry, materials, dimensions,
assembly constraints, supports, loads, and safety requirements as text. The compiler builds the 3D
model and checks whether the declared design is geometrically coherent and physically acceptable.

In plain language, the goal is:

> Write a mechanical part as code and automatically check, during compilation, whether it can be
> constructed, assembled, referenced reliably after edits, and used safely under its declared load
> case.

The intended product combines three ideas:

1. **Lean-style checking:** units, constraints, assumptions, and proof obligations are explicit.
2. **Parametric Code-CAD:** geometry is generated by a textual DSL through FreeCAD/OCCT.
3. **CAE evaluation:** analytical formulas and external solvers evaluate declared physical limits.

The current project remains a Python DSL backed by FreeCAD/OCCT. Lean 4 is a semantic reference, not
the host language for the current development cycle.

---

## 2. Problem Statement

Traditional CAD/CAE workflows have three structural weaknesses:

- **Design and analysis are separated.** Errors are often discovered only after a model is exported
  to another tool and manually prepared for analysis.
- **Binary artifacts dominate the workflow.** Geometry, load cases, and analysis settings are hard to
  review, diff, and revalidate through Git.
- **Many failures appear late.** Invalid units, impossible assembly conditions, fragile face references,
  and exceeded material limits may survive until a kernel operation or simulation fails.

This project aims to make the complete engineering intent versionable and executable:

> Define with code, discharge what can be proven, evaluate what must be simulated, and preserve the
> evidence for every decision.

---

## 3. Scope and Non-Goals

### 3.1 In scope

- Dimension-aware physical quantities and automatic unit conversion.
- Stable feature references plus geometric selectors for topology-dependent tasks.
- Enforced dimensional, geometric, assembly, tolerance, and CSG preconditions.
- First-class materials, boundary conditions, load cases, and acceptance requirements.
- Three verification tiers: analytical, bounded numerical, and trusted external solver.
- Offline execution on the air-gapped deployment target.
- Structured evidence that can be consumed by CI, self-repair, and human review.

### 3.2 Not in the initial implementation

- Migrating the current Python DSL to Lean 4, Idris 2, or F*.
- Building a new B-Rep kernel.
- Claiming that arbitrary OCCT Boolean operations are mathematically total.
- Treating a solver exit code or a single maximum-stress value as proof of safety.
- Using a display tessellation as an analysis-quality finite-element mesh.
- Supporting nonlinear materials, fatigue, contact, CFD, or multiphysics before real use cases and
  validation data justify them.
- Requiring the LLM to generate proof terms.

## 4. Integration Decisions for the Current Repository

### 4.1 Keep the existing host language and kernel path

The implementation remains:

```text
Python DSL → typed IR → FreeCAD/OCCT → verification backends
```

This preserves the existing parser, AST, reference registry, compiler, training pipeline, and offline
deployment strategy. A proof assistant may be reconsidered only if verified numerics later requires
one and its value exceeds the packaging and integration cost.

### 4.2 Extend DSL v1 instead of replacing it

The v1 grammar and sequential-edit benchmark remain frozen. Physics features belong to a versioned v2
extension. Existing v1 programs must continue to parse and execute with unchanged semantics.

The v2 surface syntax should retain the current regular form:

```text
operation(key=value, ...)
```

This is easier for a 7–14B model to generate than explicit dependent-type proof terms. The compiler,
not the model, creates and discharges proof obligations.

### 4.3 Use both symbolic references and geometric selectors

The current DSL uses stable authored names such as `body.face_top` and `hole.wall`. This is precise,
but structural edits can remove a referenced role. A selector such as “the face with outward normal
`+X` at the maximum X extent” can survive restructuring, but it may match zero or multiple faces.

The two mechanisms are complementary:

| Mechanism | Strength | Failure mode |
|---|---|---|
| Symbolic role | Exact author intent and unambiguous binding | Role may disappear after replacement |
| Geometric selector | Re-evaluates after parameter or structural changes | Can return zero, many, or the wrong semantic face |

Both must resolve into one provenance-carrying `ResolvedSubshape` representation. No implementation
may silently choose the first OCCT face or edge.

### 4.4 Treat constraints as enforced obligations

The existing `constraint` operation is currently advisory. In v2, every supported constraint returns
`pass`, `fail`, or `unknown`. `unknown` blocks automatic confirmation.

The model declares constraints; the verifier attempts to discharge them through unit normalization,
direct arithmetic, geometric rules, and an optional SMT backend. The model never emits `h_proof`.

### 4.5 Be explicit about trust

Analytical checks, conservative bounds, and FEA results do not carry the same guarantee. The result
model and UI must preserve that distinction instead of reducing everything to one green check mark.

## 5. Target Architecture

```text
┌────────────────────────────────────────────────────────────┐
│ Front end: parser, typed IR, units, references, obligations │
│ Dimension checks, selector cardinality, constraints         │
├────────────────────────────────────────────────────────────┤
│ Geometry kernel: FreeCAD / OpenCASCADE                      │
│ Profile construction, B-Rep/CSG, topology provenance, STEP  │
├────────────────────────────────────────────────────────────┤
│ Physics backends                                             │
│ Tier 1 formulas · Tier 2 bounds · Gmsh + CalculiX oracle     │
├────────────────────────────────────────────────────────────┤
│ Evidence layer                                               │
│ Status, assumptions, margins, hashes, versions, diagnostics  │
└────────────────────────────────────────────────────────────┘
```

The compiler pipeline is:

```text
parse
  → elaborate typed IR
  → normalize and check units
  → resolve symbolic references and selectors
  → discharge static constraints and CSG preconditions
  → build and validate B-Rep
  → select an applicable physics tier
  → mesh and run a solver when required
  → evaluate acceptance requirements
  → emit evidence and pass/fail/inconclusive status
```

## 6. Core Language Features

### 6.1 Dimension-aware physical quantities

Every engineering value carries a dimension and unit:

```dsl
al6061 = material(
    density=2.7 g_per_cm3,
    yield_strength=276 MPa,
    elastic_modulus=68.9 GPa
);
```

The typed representation must preserve both source and normalized values:

```text
Quantity {
    source_value,
    source_unit,
    dimension,
    canonical_value,
    tolerance?
}
```

Initial units are deliberately closed:

| Dimension | Units |
|---|---|
| Length | `mm`, `m` |
| Angle | `deg` |
| Force | `N` |
| Pressure/stress | `Pa`, `kPa`, `MPa`, `GPa` |
| Density | `kg_per_m3`, `g_per_cm3` |

ASCII unit identifiers are canonical in source code. A presentation layer may render `g_per_cm3` as
`g/cm³`. Adding a unit requires parser, conversion, serializer, and negative-dimension tests in the
same change.

Bare v1 linear dimensions remain compatible and use the configured project length unit, initially
`mm`. New non-length physical quantities must never omit units.

Invalid operations such as `Force + Length` are compile errors. Compatible units are normalized
automatically before comparison or arithmetic.

### 6.2 Refinement constraints without explicit proof terms

Creation or modification may produce obligations such as:

- all dimensions are positive;
- a profile is closed, non-self-intersecting, and has nonzero area;
- a hole stays inside the plate with a required edge margin;
- the minimum wall thickness exceeds a configured limit;
- mating parts remain compatible under worst-case tolerances;
- selected faces are concentric, coplanar, or parallel as declared.

Proof obligations are discharged automatically. A failure prevents the affected feature from being
accepted. A timeout or unsupported obligation becomes `unknown`, not success.

Tolerance values retain lower and upper bounds. Assembly checks use worst-case combinations rather
than nominal values.

### 6.3 Stable selectors and persistent naming

The initial structured selector syntax is:

```dsl
fixed_face = select_faces(
    of=bracket,
    normal=neg_x,
    at=min,
    expect=one
);

loaded_faces = select_faces(
    of=bracket,
    kind=planar,
    tag=load_surface,
    expect=many
);
```

Initial selector filters are:

- owner feature (`of`);
- topology kind;
- direction or normal;
- geometric extremum (`min`/`max`);
- explicit semantic tag;
- expected cardinality.

`expect=one` rejects zero or multiple matches. `expect=many` requires a nonempty set and produces a
stable geometric ordering.

A resolved selection records:

- source feature and history version;
- OCCT topology kind;
- centroid, area or length, orientation, and other geometric signatures;
- candidate count and each filtering step;
- model input hash;
- the reason the final entity was selected.

After regeneration, a selector that resolves to a different semantic entity is a reference break even
if it still returns one face.

### 6.4 Checked CSG preconditions

The system checks formalizable preconditions before invoking fragile Boolean operations. Examples
include positive dimensions, nondegenerate profiles, sufficient hole clearance, and nonzero expected
intersection.

This creates a useful **Total-CSG subset**, but not a universal mathematical guarantee. OCCT tolerance
effects and complex surface intersections can still fail. Therefore every Boolean operation also has
a postcondition: the kernel completed, the result is a valid B-Rep, and the observed topology satisfies
the operation-specific expectations.

### 6.5 First-class boundary conditions

Supports, loads, materials, and acceptance criteria are versioned with the geometry:

```dsl
support = fix(target=fixed_face);
load = force(target=loaded_face, value=2000 N, direction=neg_x);

case1 = static_case(
    target=bracket,
    material=al6061,
    conditions=[support, load]
);

safe = require(
    on=case1,
    result=max_von_mises,
    relation=lt,
    value=276 MPa,
    method=oracle
);
```

Boundary-condition targets must use symbolic roles, semantic tags, or selectors. Raw `Face 3` style
indices are forbidden.

### 6.6 Tiered physical verification

#### Tier 1 — Analytical

Closed-form formulas cover narrow, explicitly validated model classes such as simple beam bending or
shaft torsion. The verifier checks formula applicability before calculating a result: cross-section,
load model, boundary assumptions, linear elasticity, and small-deformation assumptions must all hold.

If applicability is not established, the result is `inconclusive`; the compiler must not apply a
convenient but invalid formula.

#### Tier 2 — Conservative bounded numerics

Results are intervals rather than point estimates. Safety is established only when the conservative
upper bound remains below the allowed limit.

Tier 2 is a research gate, not an initial deliverable. Interval arithmetic, verified numerics, dReal,
or a proof assistant should be evaluated only after real cases reveal a meaningful gap between Tier 1
coverage and Tier 3 cost.

#### Tier 3 — Trusted backend oracle

The compiler exports analysis geometry, generates a quality-controlled Gmsh mesh, creates a CalculiX
input deck, runs the solver offline, parses convergence and result data, and checks the declared
requirement.

This tier is trusted engineering computation, not formal proof. Missing boundary groups, poor mesh
quality, non-convergence, incomplete output, or version mismatch produces `inconclusive`.

## 7. Verification Result Semantics

“Compilation succeeded” must not hide the source of confidence. The system exposes these states:

| State | Meaning |
|---|---|
| `built` | Parsing and B-Rep construction succeeded |
| `checked` | Units, references, static constraints, and kernel postconditions passed |
| `proved_analytical` | An applicable closed-form model established a positive safety margin |
| `bounded` | A conservative verified interval established the requirement |
| `verified_oracle` | A recorded external analysis satisfied the requirement |
| `inconclusive` | Evidence is missing, ambiguous, unsupported, timed out, or non-converged |

The unified result object is:

```text
VerificationEvidence {
    status,       # pass | fail | inconclusive
    level,        # static | analytical | bounded | oracle
    obligation,
    assumptions,
    inputs,
    result,
    margin,
    provenance,
    diagnostics
}
```

For external analyses, provenance includes hashes of the DSL, geometry, material, boundary conditions,
mesh parameters, solver configuration, solver version, and numerical tolerances.

## 8. Proposed Module Boundaries

| Module | Responsibility |
|---|---|
| `dsl/units.py` | dimensions, unit parsing, normalization, invalid-operation rejection |
| `dsl/ir.py` | typed geometry, material, load-case, and proof-obligation IR |
| `dsl/selectors.py` | selector AST, filtering, cardinality, and stable ordering |
| `dsl/compiler.py` | faithful typed-IR to FreeCAD/OCCT execution |
| `dsl/registry.py` | authored names, dependency graph, and role re-binding |
| `verify/kernel.py` | B-Rep validity and operation postconditions |
| `verify/constraints.py` | dimensional, geometric, assembly, tolerance, and CSG obligations |
| `verify/rules.py` | engineering rule library and analytical applicability predicates |
| `physics/analytical.py` | Tier 1 formulas and reference solutions |
| `physics/intervals.py` | optional Tier 2 bounded numerics |
| `physics/mesh.py` | Gmsh export, physical groups, mesh quality, refinement studies |
| `physics/calculix.py` | input generation, offline execution, convergence and result parsing |
| `physics/evidence.py` | shared evidence schema, hashing, caching, and serialization |

These paths are proposed. They should be created only when their implementation phase begins.

## 9. Development Roadmap

### P0 — Geometry fidelity baseline

Complete before any physical result is trusted.

- Finish the unified `ProfileSpec → Edge → Closed Wire → Planar Face` path.
- Implement explicit feature-history rebuild for `edit` and `replace`.
- Complete the remaining v1 operation set.
- Build a stable role-to-subshape resolver.
- Reject every accepted-but-unimplemented parameter instead of silently discarding it.
- Test planes, directions, centers, multi-body fusion, degenerate profiles, negative dimensions, and
  Boolean failures with the real kernel.

Acceptance gate: every accepted geometry argument affects the expected B-Rep; unsupported behavior is
an explicit `CompileError`.

### P1 — Units and typed IR

- Implement the closed unit table and canonical conversion.
- Preserve source units and tolerances through parse, IR, and serialization.
- Add invalid-dimension and wrong-argument-unit tests.

Acceptance gate: conversion reference cases pass, invalid dimensional operations are always rejected,
and no round trip loses unit or tolerance information.

### P2 — Dual references and selectors

- Implement face and edge selectors for direction, extremum, topology kind, tag, and cardinality.
- Resolve named roles and selectors through the same `ResolvedSubshape` abstraction.
- Extend 3/5/10-step benchmarks with parameter sweeps and structural replacements.

Acceptance gate: zero and ambiguous matches never pass silently; every re-binding has explainable
evidence; selector resolution rate and wrong-binding rate are reported separately.

### P3 — Enforced constraints and Total-CSG subset

- Convert `constraint` from advisory syntax to executable obligations.
- Cover positive dimensions, profile validity, hole margin, wall thickness, geometric relationships,
  simple assembly fits, and worst-case tolerances.
- Introduce SMT only for obligations that direct rules cannot handle reliably.

Acceptance gate: every constraint family has pass, fail, and unknown tests; fail/unknown can never be
reported as pass; kernel Boolean failure remains a separate diagnostic.

### P4 — Boundary conditions and one Tier 1 vertical slice

- Add materials, supports, loads, load cases, and acceptance requirements to the typed IR.
- Select one real part family, such as solid-shaft torsion or rectangular cantilever bending.
- Implement applicability predicates and validate results against hand calculations and independent
  reference cases.

Acceptance gate: inapplicable formulas return `inconclusive`; valid cases report assumptions, computed
margin, safety factor, and reproducible reference inputs.

### P5 — Conditional Tier 3 pilot

Entry conditions:

- real parts include usable material, load, and support data;
- P0–P4 have passed;
- Gmsh and CalculiX can be packaged and executed on the air-gapped target.

Work:

- Map stable geometry groups to mesh boundary groups.
- Define element type, mesh quality, and convergence criteria.
- Perform at least one mesh-refinement study.
- Generate CalculiX `.inp`, execute offline, parse status, stress, displacement, and failures.
- Cache only by a complete input and toolchain hash.

Acceptance gate: missing groups, bad mesh, non-convergence, incomplete output, or stale cache entries
produce `inconclusive`. The UI displays the oracle trust boundary.

### P6 — Tier 2 research decision

Measure how many real cases are not covered by Tier 1 but do not justify Tier 3 cost. Only if that gap
is material should the project budget a separate evaluation of interval arithmetic, verified numerics,
dReal, F*, or Lean. P6 is a go/no-go decision, not a promised v1.0 feature.

## 10. Test and Evaluation Matrix

| Layer | Required positive case | Required negative case | Key measure |
|---|---|---|---|
| Units | `1000 mm == 1 m` | `Force + Length` | invalid-dimension false negatives = 0 |
| Selectors | same semantic face after parameter edit | zero, ambiguity, wrong re-binding | resolution and wrong-binding rates |
| Constraints | valid hole margin and fit | boundary crossing, tangency, tolerance conflict | fail/unknown false passes = 0 |
| Analytical | known beam or shaft result | violated applicability assumption | numerical error and assumption coverage |
| Oracle | converged reference problem | bad mesh, missing BC, non-convergence | status and evidence completeness |
| Pipeline | parameter edit triggers revalidation | stale cache or changed tool version | determinism and provenance completeness |

Training data may include a v2 construct only after its parser, validator, compiler or verifier, and
negative tests exist. Aspirational syntax must not enter the model's target distribution.

## 11. Main Risks and Required Responses

| Risk | Consequence | Required response |
|---|---|---|
| Persistent naming failure | loads or supports move to the wrong face | dual references, cardinality checks, provenance, wrong-binding benchmark |
| Boolean tolerance failure | legal syntax crashes or produces invalid B-Rep | checked preconditions plus kernel postconditions |
| Continuous physics vs. discrete logic | FEA result is mistaken for proof | tiered result states and explicit trust boundary |
| Mesh-dependent result | unsafe design passes on a poor mesh | quality gates and refinement/convergence studies |
| Missing real load cases | physics track has no valid evaluation target | gate P5 on real materials, loads, and supports |
| LLM grammar complexity | parse and edit accuracy degrade | regular structured syntax; compiler-generated obligations |
| Offline dependency burden | deployment target cannot reproduce results | package and test all backends without network access before adoption |
| Stale cached evidence | changed geometry reuses an old result | complete content-addressed cache key and version hashes |

## 12. Reference Systems

| Area | Systems | What to study |
|---|---|---|
| Types and proofs | Lean 4, Idris 2, F* + Z3, dReal | dependent/refinement semantics, unit types, automatic obligation discharge |
| Geometry | OpenCASCADE, FreeCAD, CadQuery/OCP, OpenSCAD, Fornjot | B-Rep, Booleans, selectors, topology history, Code-CAD syntax |
| Meshing and FEA | Gmsh, Netgen, CalculiX, FEniCS | physical groups, quality meshes, input generation, solver integration |
| CFD, if later justified | OpenFOAM | offline CFD workflow and boundary-condition mapping |
| Research | Penrose, Julia SciML, POPL/PLDI geometric-programming work | constraints, differentiable design, verified geometric programming |

These are design references, not automatic dependency choices. Every dependency must satisfy the
project's offline deployment constraint.

## 13. Immediate Next Work

The next development sequence is intentionally narrow:

1. Complete the geometry work listed in [`compiler_status.md`](compiler_status.md), especially the
   stable role resolver, feature-history rebuild, and remaining operations.
2. Freeze the minimal v2 syntax for units and structured selectors without changing the v1 benchmark.
3. Implement `Quantity` dimensions and the typed IR with negative tests.
4. Implement one end-to-end selector path with cardinality and provenance.
5. Make one existing constraint executable and return structured evidence.
6. Build one Tier 1 vertical slice for a single real part family.
7. Decide whether the available real-part data is sufficient to enter the Gmsh/CalculiX pilot.

This order prevents the physics layer from evaluating geometry that the compiler did not faithfully
construct and prevents the training pipeline from learning syntax that the runtime cannot verify.
