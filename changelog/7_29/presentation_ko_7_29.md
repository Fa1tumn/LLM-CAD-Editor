# M1 랩미팅 발표 자료

> 세부 내용: `CHANGELOG_7_29.md` 참고

이번 주에 한 일을 몇 가지로 나눠서 말씀드리겠습니다.

## 1. 프로젝트 골격

연구 계획의 네 가지 연구 질문(RQ)에 맞춰 프로젝트 전체 모듈 구조를 먼저 잡았습니다. `dsl/`은 DSL 정의와 파서, `editor/`는 편집 엔진, `verify/`는 나중에 만들 4중 검증 루프, `eval/`은 평가 프레임워크, `data/`는 데이터 합성과 실제 부품 데이터, `deploy/`는 사내망 배포를 담당합니다. 이번 주에 구현한 두 파일을 제외하면 나머지 모듈은 아직 인터페이스만 정의된 상태고, 각 모듈이 어느 마일스톤에서 채워질지 TODO로 표시해뒀습니다.

그리고 12개월치 마일스톤(M1–M12)을 주 단위 실행 계획으로 펼쳐서, 매주 할 일을 체크리스트 형태로 정리했습니다.

## 2. DSL v1 문법 확정

이번 주의 핵심입니다. `dsl/grammar.md`에 이 언어의 전체 스펙을 정리했습니다.

**연산 집합**: 기본 연산은 선행 연구에서 쓰던 `sketch`/`extrude`/`revolve`/`fillet`/`chamfer`/`pocket`/`groove`를 그대로 가져왔고, 계속 쓰이긴 했지만 한 번도 정식으로 정의된 적 없던 `edit`(단일 값 파라미터 수정)도 이번에 정의했습니다. 핵심적으로 새로 추가한 건 복합 편집을 위한 연산 4개——`replace`(특징 교체, 하위 참조 재바인딩을 트리거함), `pattern`(배열 복제), `mirror`(대칭), `constraint`(제약 선언)——입니다.

**참조 문법**: 점 표기 참조(`body.face_top`)와 배열 인스턴스 참조(`pat1[*]`, `pat1[2]`).

**파생 이름 role**: 7개로 확정했습니다——`face_top`, `face_bottom`, `axis`, `wall`, `floor`, `edge_top`, `edge_bottom`——그리고 각 연산이 어떤 role을 만들어내는지 표로 정리했습니다.

그리고 이전부터 미뤄뒀던 설계 결정 5가지도 이번에 확정했습니다:

- `edit`과 `replace`의 경계——연산 종류가 그대로고 값 하나만 바뀌면 `edit`, 연산 종류 자체가 바뀌면(모양이 비슷해 보여도) `replace`를 쓰고, 이 경우 재바인딩 검사가 트리거됩니다.
- `constraint`가 최소한 지원해야 할 종류——치수 쪽은 equal/range/ratio, 기하 쪽은 concentric/coplanar/parallel부터 지원하기로 했고, `config/default.yaml`에 이미 정의된 검증 임계값들과 맞아떨어지도록 골랐습니다.
- `pat1[*]` 같은 배열 참조를 검증 단계에서 어떻게 전개할지——`pat1[0]`부터 `pat1[count-1]`까지 전개하고, count는 해당 `pattern` 문에서 가져옵니다. 실제 전개 로직 구현은 M6 검증 단계로 미뤘습니다.
- 파생 이름 role의 전체 목록——위에서 말한 7개.
- 파서를 lark/antlr 같은 파서 생성기로 만들지——안 씁니다. 손으로 짠 재귀 하강 파서로 충분하고, 문법 자체가 크지 않아서 굳이 의존성을 추가할 필요가 없었습니다.

## 3. 파서 구현 + 테스트

문서에 규칙만 적어놓은 게 아니라 실제로 구현했습니다.

`dsl/ast.py`에는 AST 노드 타입들——문장, 참조, 단위가 붙은 숫자, 중첩된 연산 호출——을 정의했고, `replace`/`pattern`/`mirror`/`constraint` 이 4개 새 연산이 필수 인자를 다 채웠는지 검사하는 함수도 넣었습니다.

`dsl/parser.py`가 실제 파서인데, 두 단계로 되어 있습니다. 먼저 토큰화(tokenize)——DSL 텍스트 전체를 단어 단위로 쪼갭니다. 그다음 재귀 하강(recursive descent) 방식으로 이 단어들을 다시 구조화된 문장으로 조립합니다. 재귀 하강이란, 문법의 규칙 하나하나가 함수 하나에 대응하고 함수들끼리 서로 호출하는데, 문법 자체가 중첩될 수 있는 부분——예를 들어 연산 호출 안에 또 다른 연산 호출이 들어가는 경우——은 해당 함수가 자기 자신을 다시 호출하는 식으로 처리된다는 뜻입니다. `replace(target=body, with=extrude(profile=hex(r=20), length=250))`처럼 "연산 안에 연산 안에 연산"이 들어간 문장이 정확히 파싱되는 것도 바로 이 재귀 덕분입니다.

pytest 테스트 13개를 작성했고, 문법 스펙에 나온 모든 예제(RQ2에서 쓸 5단계 연속 편집 체인 포함), 세 가지 참조 형식, 잘못된 호출 5가지가 제대로 걸러지는지, 문법 오류가 정확한 줄 번호를 알려주는지, 단위가 붙은 값이 제대로 파싱되는지까지 다 검증했습니다. 13개 전부 통과했습니다.

## 4. 실제 동작 결과

몇 가지 실행 결과를 보여드리면:

가장 복잡한 문장인 `replace(target=body, with=extrude(profile=hex(r=20), length=250))`을 파서에 넣어보면, `with` 인자가 독립된 `extrude` 연산 노드로 정확히 분리되고, 그 `extrude`의 `profile` 안에는 또 `hex` 노드가 중첩되어 들어갑니다. 3중 중첩이 전부 정확하게 나왔습니다.

일부러 잘못된 입력도 넣어봤습니다——예를 들어 `replace`에서 필수인 `with`를 빼먹거나, `pattern`의 `type`에 존재하지 않는 값을 넣는 경우——이런 경우 전부 파싱 단계에서 바로 에러가 나서 걸러지고, 잘못된 편집 명령이 뒤쪽 모델링 과정으로 넘어가지 않습니다.

문법 오류도 정확히 몇 번째 줄인지 알려줍니다. 세미콜론을 빼먹으면 "expected RPAREN, got IDENT 'body' (line 2)" 같은, 줄 번호가 포함된 에러가 나오는데, 이건 나중에 self-repair 루프에서 에러를 모델에 다시 피드백할 때 유용하게 쓰일 겁니다.

숫자에 단위가 있든(`250 mm`) 없든(`250`) 같은 타입으로 파싱되기 때문에, 뒤에서 이걸 처리하는 코드가 두 가지 경우로 나눠 처리할 필요가 없습니다.
